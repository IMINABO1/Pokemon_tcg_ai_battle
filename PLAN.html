Pokémon TCG AI Battle — Phase 1 Implementation Plan (Heuristic + PIMC Search)

Context

Competing in "The Pokémon Company - PTCG AI Battle Challenge Simulation" (Kaggle), a two-player imperfect-information Pokémon TCG ladder judged by continuous matchmaking and a Gaussian skill rating system. Goal: top 10 of roughly 5,000 teams (99.8th percentile), not just a working submission. Entry and merger deadline August 9, 2026. Final submission deadline August 16, 2026. Ladder converges around August 31, 2026.

Naive single-guess search is theoretically exploitable, but PIMC/ISMCTS-style search (guess plausible opponent hands, search each, average the results) is the practical approach used in real trading-card-game bots. Pure self-play reinforcement learning is powerful but risky to attempt cold — it can quietly diverge or "cycle" without safeguards (confirmed via the Lux AI Kaggle competition and academic NFSP research), and building it well is a real infrastructure project on its own. The plan ships a heuristic-plus-search agent first, since it can be working and safely submitted within days, then layers in a self-play-trained model on top of the same scaffolding — with a guaranteed fallback to the proven search agent if the learned version underperforms.

The competition provides a real forward-model API (search_begin / search_step in the cg package) — you hand the actual C++ game engine a hypothesized full game state, including a guessed version of the opponent's hidden cards, and it steps the real rules engine forward. This is the centerpiece the whole architecture is built around.

Key engine facts (confirmed by reading the actual engine source)

  • search_begin / search_step / search_end / search_release are backed by a real clone-and-step C++ search tree, not a mock.
  • The random number generator is shared across every node of one search tree. Never explore sibling branches of one search tree in parallel or across threads — always traverse one tree sequentially. If we ever want to use both CPU cores for search, it must be separate OS processes, each with its own engine handle, not threads sharing one handle.
  • search_step can silently auto-advance through several no-choice sub-decisions before returning the next real choice point — never assume the next prompt is the one you expected.
  • The SelectContext field in the observation is explicitly noted in the engine's own source as unreliable. All decision logic must branch on SelectType / Option.type only, never on SelectContext.
  • search_begin requires a complete guess — it will reject a guess that leaves the opponent's face-down active Pokémon unresolved.
  • The engine supports reshuffling a hypothesized deck mid-search internally, but this capability is not exposed to Python — a real, minor capability gap; workable around since each decision re-samples a fresh guess anyway.
  • The local game driver (cg.game.Battle) is a single global object — only one battle can run at a time per Python process. The local test harness must use multiple processes, not threads, to run many games at once.
  • Deck legality: exactly 60 cards; max 4 copies of any named card except Basic Energy (unlimited); max 1 ACE SPEC card; at least 1 Basic Pokémon required.
  • There is a 3,000-action hard cap per game, but no documented per-move "thinking time" limit anywhere in the provided engine source. This is the single biggest open unknown, and the plan treats probing it (via an early real submission) as a top priority.
  • The canonical source of card data at runtime is the engine's own all_card_data() / all_attack() functions, not the provided CSV file (which is for offline research only).

1. Repo scaffolding

Create a new agent folder as a sibling to the existing read-only competition folders. This is the git-tracked dev workspace.

Structure:

  • pyproject.toml — zero or stdlib-only runtime dependencies; dev tools like pytest/pandas kept separate
  • cg — the vendored engine bindings, copied unmodified from the sample submission, never hand-edited
  • src/ptcg_agent/
    • main.py — thin entrypoint: reads deck.csv, delegates everything else to policy.py
    • deck.csv — current candidate deck
    • carddb.py — card knowledge base
    • determinize.py — own-state tracker plus opponent belief and sampling
    • search.py — PIMC rollout and root-averaging search
    • evaluate.py — the scoring function, evaluate_state
    • policy.py — routes each decision type to the right handler
    • budget.py — wall-clock time budgeting and cutoffs
    • logging_utils.py — structured decision logging, dev/test only, stripped from the shipped build
    • config.py — one importable dictionary of tunable numbers (search budget, evaluator weights, etc.)
  • tests/ — unit tests for card lookups, deck legality, and state-tracking logic
  • decks/ — candidate decklists plus notes on each one's game plan
  • harness/ — the local match-running tools used for testing before ever submitting
  • scripts/ — build_submission.sh (packages the .tar.gz) and validate_submission.py (smoke tests it)
  • dist/ — build output, not checked into git

Rules: never reimplement the engine bindings — always copy them fresh from the competition-provided sample at build time. Keep main.py a thin wrapper so the Kaggle-facing entrypoint stays stable while everything else iterates. Runtime code should only ever import the standard library and the cg package — no pandas, no pytest, nothing that might not exist on Kaggle's servers.

2. Card knowledge base

Load once at startup from the engine's own all_card_data() and all_attack() functions (not the CSV, which is for human research only):

  • Lookup tables: card ID to card data, attack ID to attack data, card name to card data, the set of Basic Energy IDs (no copy limit), the set of ACE SPEC IDs (max 1 per deck)
  • A cheap "can this attack be paid for" check, used to prune search options
  • A first-order damage estimate (base damage, weakness, resistance) — explicitly not a full text parser
  • A small hand-curated table of special-case damage rules for the 10-20 highest-value cards actually relevant to our deck or common threats

Explicitly out of scope: a general parser for the roughly 2,000 rows of free-text attack and ability effects. That is a multi-week project on its own. Instead we lean on the real engine to resolve what a move actually does — the heuristic only needs to score the resulting board, not predict the effect text in advance. This is a permanent, accepted limitation, not something we're planning to eventually finish.

3. Deck selection

Build a focused, single-energy-type efficient-attacker deck rather than adapt the sample's mill deck. Reasoning: a deck whose win condition is "attach one energy, hit hard, repeat" is much easier for a heuristic-plus-shallow-search agent to pilot correctly than a combo or mill deck needing precise sequencing — and early on, our own play quality is the bottleneck, not deck power.

Leading candidates already identified in the card pool: Ceruledge (220 damage for 1 Fire energy) or Palafin ex (250 damage for 1 Water energy after its setup ability). First pass deck: 3-4 copies of that attacker's evolution line, a handful of strong draw/search Supporter cards for consistency, 12-16 matching Basic Energy (much less than the sample deck's 35, since the cost per attack is low), one ACE SPEC card if it fits, all checked against the legality rules before ever testing it.

Treat this first deck as a placeholder to unblock testing, not a final answer. Once the local harness exists, build 3-5 candidate decklists and run them against each other locally (same agent piloting all of them) to get real relative-strength data. Swapping deck.csv later never requires touching the agent's code.

4. Core agent architecture

4.1 Top-level dispatch

The agent function: if there's no decision to make yet (the very first call, which is really just "hand over your deck.csv"), return the deck. Otherwise, try to make a real decision; if anything throws an exception, fall back to the simplest possible legal move rather than ever crashing and forfeiting the match.

Real decisions are split into two paths:

  • Small or cheap decisions (yes/no prompts, choosing how many cards, single-legal-attack situations, switching/retreating): resolved with quick heuristic rules or a shallow one-move-ahead check using the scoring function. Not worth the cost of a full guess-and-search cycle.
  • Decisions that meaningfully change the game (which card to play, whether to attack now, where to attach energy): routed through the full search.
  • Big combinatorial choices (searching the deck for a card matching some condition, where there might be 20+ legal options): first narrowed down heuristically to a short list of plausible choices, then only that short list gets scored — never blindly search every option.

4.2 Guessing the hidden information (determinization)

Our own deck and prize cards are not actually a guessing problem — we know the multiset of cards we built our deck from, so we can track exactly which of our own cards remain unseen versus which specific ones ended up as our face-down prizes, purely by process of elimination as the game reveals information. This should be implemented as exact bookkeeping, not random sampling, since a bug here would corrupt every guess we make.

The opponent's hidden cards are a real guessing problem. We maintain a running belief about their hand/deck/prizes, updated every time a log reveals something about what they played. For anything still unknown, we sample a plausible guess — weighted toward card types/colors we've already seen them play, never a uniform random guess across the entire 1,267-card pool, since that would produce absurd, unhelpful guesses.

Every guess must independently pass the same legality checks as a real deck (60 cards, copy limits, etc.) before we hand it to the engine, with a bounded number of retries and a safe generic fallback guess if we can't produce a legal one.

Budget: guess roughly 6-10 different plausible opponent hands per real decision, evaluate each one in sequence (never in parallel within one process, per the shared random-number-generator constraint above), with a conservative total wall-clock budget of about 1.5-2.5 seconds per decision as a placeholder — this number gets tuned once we learn the real per-move time limit from an actual Kaggle submission.

4.3 The actual search

We use a shallow "Perfect Information Monte Carlo" search rather than a deep, fully-shared search tree (the more sophisticated "ISMCTS" approach), because a deep shared tree needs many more iterations to pay off than our time budget likely allows. The recipe: for each guessed opponent hand, pretend it's the real hand (now there's no hidden information left, i.e. "perfect information"), search a few moves deep, score the resulting positions with our scoring function, then average the results across all the guessed hands to decide on the actual move. This is the standard, resource-realistic version of "search under uncertainty" used by real trading-card-game bots.

Always release/free every explored search node when done with it — the engine's search memory pool has no automatic cap, so failing to clean up would leak memory across a long match.

4.4 The scoring function

A weighted sum of separately-testable sub-scores, all bundled into one importable dictionary of weights so they're easy to tune later:

  • Prizes taken (this is literally how you win, so it's weighted highest)
  • Board HP balance (our Pokémon's health percentage vs. theirs)
  • Immediate knockout threat, in both directions (distinct from raw HP — "one more hit and it's dead" matters more than the HP number alone suggests)
  • Energy tempo (do we actually have enough energy attached to use our best attack right now)
  • Board development (how many Pokémon in play, evolution progress, bench usage)
  • Hand quality (card count, whether we have a usable Supporter or attack available)
  • Status conditions (poisoned, paralyzed, etc. — penalty for us, bonus if the opponent has one)
  • A large score override the instant the game is actually won or lost

5. Local test harness

Built directly on the engine's own local match-driving functions — no need to touch Kaggle's actual servers to test.

Because the local battle driver is a single shared object per process, running many games at once requires multiple separate processes, not just multiple threads.

Match types to run locally: our agent vs. the sample's random-move agent (a basic sanity check), our agent vs. the sample's mill deck, our agent vs. itself (checking for crashes/consistency), and round robins across our 3-5 candidate decklists. Track win rate, average game length, and how often the safety fallback got triggered (a good proxy for hidden bugs) for each.

6. Submission packaging and validation

Building the submission:

  1. Start from a clean staging folder
  2. Copy in our source code (excluding dev-only logging code)
  3. Copy main.py to the top level of the package (required by Kaggle)
  4. Copy in whichever candidate deck.csv we're actually shipping
  5. Copy in a completely fresh, unmodified copy of the engine bindings folder
  6. Package it as a .tar.gz and confirm main.py really is at the top level
  7. Check the total size against the roughly 197 MB limit (currently a non-issue — the compiled engine binaries are only a few megabytes)
  8. Hard-fail the build (not just warn) if the deck fails our legality checker

Before ever submitting, smoke-test the actual packaged file (not just the dev copy): does it run with nothing but the standard library and the bundled engine bindings, does reading the deck file work the way Kaggle expects, does a real local match run clean with zero crashes, do all the tricky edge-case decision types get handled (forced discards, ability ordering, zero-option selections, the very first deck-request call), does the safety fallback path actually exist in the shipped build and is it itself simple enough that it cannot fail.

7. Hooks for the later learning phase

Even though Phase 1 is heuristic-based, the code is structured so a learned model can be swapped in later without a rewrite:

  • The scoring function has one clean interface, so a trained neural network can later replace it without touching the search logic at all
  • Every decision made during local test matches gets logged in a structured format (state, action taken, eventual outcome) — exactly what's needed to later train a model, whether that's supervised pretraining or full self-play reinforcement learning
  • The scoring weights live in one plain dictionary specifically so they can be automatically tuned later by an overnight loop that tries different weights, runs a batch of test matches, and keeps whatever wins more — using the school's compute cluster for parallel match simulation even before any actual neural network exists
  • The opponent-belief-guessing logic is similarly a clean, swappable piece if we ever want a smarter, learned way of guessing what the opponent is holding

8. Week-by-week timeline (compressed)

Compressed from the original 5-week draft to buy a full extra week for the self-play reinforcement learning track, since a search-only agent is unlikely to be enough on its own for a top-10-of-5,000 finish.

Week 1 (Jul 13-19): Build the scaffolding, the card knowledge base, the legality checker, and a first placeholder deck. Ship a basic heuristic-only agent (no search yet) that is legal and cannot crash. Submit it to Kaggle by day 3 or 4 of the week — early, specifically to start the clock on discovering the real per-move time limit, since that's the biggest open unknown driving the search design. Build the local multi-game test harness and use it to A/B test 3-5 candidate decklists while that first submission racks up ladder games in the background.

Week 2 (Jul 20-26): Build the guessing logic and the PIMC search, tune the time budget using whatever real signal came back from the Week 1 submission, and confirm in local testing that the search-based agent clearly beats the heuristic-only one before trusting it.

Week 3 (Jul 27-Aug 2): Submit the search-based agent and harden it — edge cases, deck finalized from real local and ladder data. Goal: a solid, locked-in submission a full week ahead of the August 9 entry deadline. In parallel, start the self-play reinforcement learning track: build the infrastructure to generate training data from simulated self-play games and set up training on the university GPU cluster.

Week 4 (Aug 3-9, entry deadline): Full week focused on the reinforcement learning track — training a learned model via self-play to eventually replace the hand-built scoring function, with explicit safeguards against the model quietly "cycling" or collapsing during training (a documented real risk with naive self-play), continuously checked against the already-locked-in search agent in local testing.

Week 5 (Aug 10-16, final deadline): Decision point around August 14 — ship the learned-model version only if it's clearly and consistently beating the search-only agent in local testing; otherwise ship the proven search-only agent, which is never at risk of being lost since it's already locked in. Reserve the final day or two purely for validation, with no risky last-minute changes.

After August 16: no further submissions possible. Use remaining GPU cluster time to continue the learning track for future reference, or simply monitor final ladder placement.

Explicit risks and how the plan handles each

  1. Unknown per-move time limit — handled with a conservative default budget, an early real submission specifically to measure it, and a fast fallback path that can always answer quickly if the budget runs out.
  2. Random number generator shared across one search tree — handled by only ever exploring one tree sequentially; any future parallelism must be separate processes, never threads sharing one engine handle.
  3. The unreliable SelectContext field — handled by branching only on SelectType/Option.type everywhere.
  4. No way to reshuffle a guessed deck mid-search from Python — likely a non-issue since each decision re-guesses from scratch anyway; flagged for early testing.
  5. Deck chosen with no real strength data at first — handled with an explicit plan to A/B test several candidate decks locally before treating any of them as final.
  6. No general parser for attack/ability text — a permanent, accepted limitation; the real engine is always the source of truth for what a move actually does.
  7. Bugs in our own deck/prize tracking would corrupt every guess we make — handled with dedicated unit tests, since this is exact bookkeeping, not sampling, and should be fully deterministic.
  8. The local test harness can only run one match per process at a time — handled by using multiple processes for the harness, not multiple threads.
  9. Our development machine and Kaggle's servers likely run different operating systems — handled by always shipping every provided version of the compiled engine binary, letting the bindings pick the right one automatically at runtime.
  10. The self-play reinforcement learning track might not converge in time, or might quietly "cycle" into a bad strategy — handled by building in known anti-cycling safeguards from the start (rather than naive self-play), and by treating the already-locked-in search-only agent as a guaranteed fallback that only gets replaced if the learned version demonstrably wins more games locally by the Week 5 decision point.

Notes and clarifications

Plan in one paragraph: we can't see the opponent's cards, but we do have the real game engine in our pocket. So instead of guessing once, we make several different reasonable guesses about what the opponent might be holding, replay each guess forward in the real engine to see how a move plays out, and average the results to decide what to actually do — that's the whole trick. On top of that guessing-and-searching agent, we're using a simple hand-built scorecard (prizes taken, health, board state, etc.) instead of a trained model at first, because a trained self-play model is a multi-week project that can quietly go wrong (a real, documented failure mode) if rushed — so we ship the safer version first and only swap in a learned model later if it demonstrably wins more.

What "ply" means: one single move by one single player, not a full turn. A 1-ply lookahead means: try each option, imagine the very next position after making it, score just that position, and stop — no further guessing about what happens after. It's the cheap version of lookahead, used for small/easy decisions. A 2-ply lookahead would also imagine the opponent's best response before scoring, and so on, each additional ply going one move deeper into the "if I do this, then they do that" chain.

What "PIMC" means (Perfect Information Monte Carlo): our chosen search method. Normal game-tree search assumes you can see the whole board with no secrets. Our game has secrets (the opponent's hand). PIMC's trick: pretend the secret doesn't exist, one guess at a time. Guess a plausible opponent hand, treat that guess as if it were simply true (no hidden information left — "perfect information"), and run ordinary search on that pretend-perfect-information version of the game. Repeat with a handful of different guesses, then average the results across all of them to pick the actual move. It's the simpler, cheaper cousin of ISMCTS, chosen specifically because it fits the 2-vCPU inference budget, whereas the fancier method needs more compute to pay off.
